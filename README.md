# Enterprise Graph RAG Architecture Showcase

> **⚠️ 보안 안내 (Security Notice)**  
> 본 저장소는 기업 정보 보안 및 기술 유출 방지를 위해 **사내 비즈니스 로직(프롬프트, 내부 데이터, 인프라 연결 정보)이 추상화(Skeletonize) 처리된 아키텍처 쇼케이스용 코드**입니다. LangGraph 기반의 파이프라인 설계 사상과 코드 구조(Architecture Blueprint)를 확인하는 용도로 제공됩니다.

## 주요 아키텍처 (Architecture)
- **LangGraph 기반 Multi-Agent Workflow**: 질문 분석, 계획 수립(Plan), 하위 쿼리 실행(Execute), 검색 증강(RAG), 검증(Groundedness Check)을 수행하는 비동기 상태 머신 구조
- **Knowledge Graph & Ontology Router**: 방대한 사내 문서 체계를 Graph DB(Neo4j) 기반의 지식 그래프(Knowledge Graph) 및 온톨로지로 구조화하여, 쿼리 의도와 문서 간의 논리적 관계(Relationships)를 추론해 최적의 문서 컬렉션으로 동적 라우팅
- **자연어 최적화**: Kiwi 형태소 분석기를 활용해 사용자 자연어 질문을 검색 엔진용 키워드로 정제 (기술 용어, 약어 보존)

## RAG 성능 평가 결과 (Evaluation)

본 RAG 파이프라인은 고객사 테스트를 거쳐 <b>97% ~ 100%</b>의 높은 최종 정답률을 달성했습니다. 

### ⚠️ 100%가 아닌 이유? (의도적 모호성 및 Edge Case)
AI Agent의 문서 탐색 및 답변 생성 능력은 사실상 100%이나, 1~3%의 차이는 <b>'질문의 모호함'과 '고객사의 엄격한 채점 기준'</b>에서 발생했습니다.

**[예시 상황]**
> **사용자 질문**: *"직원의 인사평가 시기와 결과는 다음 해 성과연봉에 어떤 방식으로 반영돼?"*

단순 "직원"으로 질문이 들어왔을 때, AI는 정규직 기준의 완벽한 규정 답변을 도출했습니다. 하지만 고객사의 평가 기준에서는 <b>"기간제 근로자에 대한 규정 내용 미포함 시 오답"</b>으로 엄격하게 처리되었기 때문에 감점이 발생했습니다. 

### 핵심 결론 (Conclusion)
위와 같이 고객사의 특수한 요구 조건(Hidden Intent)에 따라 답변 범위가 달라지는 케이스를 제외하면, **AI가 질문 의도를 잘못 파악하거나 근거 문서를 아예 찾지 못해 답변에 실패하는(Hallucination / Retrieval Fail) 치명적 에러는 전체의 1% 미만**으로 철저한 아키텍처 검증을 완료했습니다.

## Troubleshooting & Engineering Experience (문제 해결 경험)

본 프로젝트를 구축하며 직면했던 5가지 핵심 기술적 과제와 해결 과정입니다.

**Q1. 사용자의 복합적인 질문(예: A규정과 B지침의 차이)에 대해 RAG가 답변을 잘하지 못하는 현상은 어떻게 해결했나요?**  
**A.** 초기에는 단일 검색(Single Retrieval) 구조를 사용했기 때문에 복합 질문에 대한 문서 커버리지가 매우 낮았습니다. 이를 해결하기 위해 <b>LangGraph 기반의 Multi-Agent 아키텍처(Plan & Execute 패턴)</b>를 도입했습니다. 먼저 'Planner 노드'가 사용자의 복합 질문을 독립적인 여러 개의 하위 질문(Sub-queries)으로 분해합니다. 이후 'Executor 노드'가 각 하위 질문에 대해 검색을 수행하고, 최종적으로 조각난 정보들을 취합해 답변을 생성하는 구조를 구현하여 복잡한 질문에 대한 정답률을 획기적으로 끌어올렸습니다.
   - **결과: 통상 정답률 - 85% > 97~100%**

**Q2. 하위 질문(Sub-queries) 검색 과정에서 응답 속도(Latency)가 느려지는 문제는 어떻게 해결했나요?**  
**A.** 초기에는 분해된 하위 질문들을 메인 플로우(Main Flow) 안에서 순차적(Sequential)으로 검색하도록 구현했습니다. 하지만 질문이 3~4개로 늘어날 경우 전체 응답 시간이 지나치게 길어지는 병목 현상이 발생했습니다. 이를 해결하기 위해, 메인 플로우의 부담을 줄이고 검색 로직을 <b>서브 플로우(Sub-flow)로 분리하여 병렬 검색(Parallel Search)</b>이 가능하도록 아키텍처를 재설계했습니다. 그 결과, 여러 하위 질문을 동시에 처리할 수 있게 되어 검색 단계의 응답 시간을 크게 단축시켰습니다.
   - **결과: 최대 140s > 최대 120s 이내**

**Q3. 검색된 문서들 간에 내용이 충돌하거나(예: 구 버전 vs 신 버전 규정) 정보가 부족한 경우는 어떻게 처리했나요?**  
**A.** RAG의 고질적인 문제인 환각(Hallucination)을 막기 위해 파이프라인 내부에 **독자적인 교차 검증(Groundedness Check & Conflicting Points) 로직**을 추가했습니다. 검색된 문서들을 바로 답변 생성에 넘기지 않고, 별도의 평가 LLM(Scoring LLM)이 '검색된 문서가 질문의 조건에 부합하는가', '문서 간 상충되는 내용은 없는가(최신 개정본 우선 원칙 등)'를 10점 만점으로 먼저 채점합니다. 정보가 부족하다고 판단되면 즉시 답변 생성을 멈추고 후속 검색 질의를 다시 던지는 동적 검증 루프를 구현하여 답변의 신뢰성을 보장했습니다.

**Q4. 답변 생성 시간이 길어져 사용자 경험(UX)이 저하되는 문제는 어떻게 해결했나요?**  
**A.** 다수의 문서를 검색하고 추론하는 과정에서 최초 토큰 응답 대기 시간(TTFT: Time To First Token)이 길어지는 현상이 있었습니다. 사용자 이탈을 막기 위해 **서버-클라이언트 간 비동기 SSE(Server-Sent Events) 스트리밍**을 도입했습니다. LangGraph의 비동기 실행 흐름(`ainvoke`)을 바탕으로, 내부 노드들이 상태(Status)를 바꿀 때마다 "현재 규정 문서를 탐색 중입니다...", "관련 부서 지침을 확인 중입니다..."와 같은 진행 상황을 중간중간 실시간으로 클라이언트에 푸시하도록 개선하여 체감 대기 시간을 대폭 줄였습니다.

**Q5. 병렬 검색 도입 이후 또 다른 성능 이슈(Latency)는 없었나요?**  
**A.** 서브 플로우를 통한 병렬 검색(Map-Reduce)으로 속도를 개선했지만, 하위 쿼리가 늘어날수록 다수의 LLM 호출이 동시다발적으로 발생하여 궁극적으로는 토큰 소모량과 시스템 부하가 급증하는 새로운 한계에 부딪혔습니다. 실시간 챗봇 환경에서는 일관된 속도가 중요했기에, 무거운 Map-Reduce 처리 방법론을 과감히 제거하고 **단일 쿼리 기반의 순차적 온톨로지 라우팅(Sequential Routing) 및 조기 종료(Early Stopping)** 아키텍처로 선회했습니다. 온톨로지 그래프를 바탕으로 가장 가능성 높은 컬렉션을 우선 검색하고, 답변에 충분한 정보가 모이면 나머지 검색을 과감히 스킵하도록 파이프라인을 최적화하여 기존의 정답률은 유지하면서 최종 Latency를 극적으로 안정화시켰습니다.
   - **결과: 120s > 50s 이내**
